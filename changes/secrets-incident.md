### Added

- **`kit secrets list` and `kit secrets incident <backend>` give a vault-vendor incident a response path.** After 1Password's November 2026 incident (kit-research#232) kit could not list the keys it sources from one backend (only `vault-migrate --dry-run` did, as a side effect), rotate them as a set, or tell whether a rotation changed anything (`secrets validate` checks that a key resolves). `list [--backend <name>] [--json]` prints key names with the `<KEY>_EXPIRES_AT` hint and the last rotation kit recorded; it never reads a value. `incident <backend>` prints each key's rotation command (`--from-cli`, the Supabase Management API path, or manual), names the CLI binary values are read through, and writes a fingerprint snapshot: HMAC-SHA256 under a random per-snapshot key, owner-only (`src/utils/secure-perms.ts`), in `.kit/incident/<backend>.json`, refused unless git ignores it. `--verify` re-reads each value and exits 0 only when every key changed; a value it cannot re-read is "not verified", never "changed". A missing, widened, corrupt or re-keyed snapshot is an error, and only `--new-snapshot` replaces one. Every run writes a `secrets.incident` audit row with names and outcomes, never values. kit does not rotate remote credentials in a batch: minting and revoking stay a person's step. A vendor-CLI pin check has a named hook (`CliIdentityCheck`) and is not wired yet. Tested on Linux; Windows runs in CI; macOS is unverified.
