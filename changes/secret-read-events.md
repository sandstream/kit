### Added

- **Every secret read through kit is now recorded in the audit chain, with `[governance]` on or off.** `kit secrets` with the default config wrote no audit event at all: the only record of a read was the governed `secrets.generate`, and `withGovernance` returns before any audit when governance is off. kit now appends one `secrets.read` event per store, through the same hash-chained, anchored append that already records writes, whenever it resolves or hands on a secret: `kit secrets` (and `sync`, `validate`, `onecli register`), the MCP `kit_secrets` tool, `kit run` and MCP `kit_run` (the `.env.local` names given to the child), the exec-broker (the env names it hands over), the availability probes in `kit check`, `kit fix`'s deploy step and the branch-protection audit. The event carries the key NAMES, the store, the kit surface (`via`), the agent harness kit detected (Claude Code or Codex) and `[governance.agent]` where the caller has the config; never a value or a digest of one. The record is written before the value is fetched, and when it cannot be written kit refuses the read (fail closed), so a damaged or unwritable `.kit-audit.jsonl` now stops `kit secrets` and `kit run` until `kit audit verify` passes. Governance-only behaviour is unchanged: permission, revocation, budget and approval checks, the agent stamp on governed events and the opt-in remote push. `kit audit secrets` lists these reads per key. Coverage: reads through kit only; a process that opens `.env.local` itself is not visible. Found by kit-research note kms-decrypt-evidence-vs-kit.
