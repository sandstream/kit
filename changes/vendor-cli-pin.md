### Added

- **`kit tools pin` pins the vault and cloud CLIs kit hands secrets through, and kit refuses to run one that changed.** kit ran whichever `op` (or `infisical`, `bw`, `doppler`, `vault`, `aws`, `gcloud`, `az`, `gh`) came first on PATH, and a 20-line shell script named `op` got `✓ op 2.30.0`. Following 1Password's November 2026 incident, which reached the vendor's git and CI/CD (kit-research#232), `kit tools pin [<tool>...]` records each CLI's realpath (a Homebrew symlink hashes its Cellar target), SHA-256 and `--version` in `.kit/cli-lock.json` under `identity`, per `<platform>-<arch>`, with home-directory paths stored as `~/…`. `kit check` adds a `vendor CLI: <tool>` security row (`supply-chain`): fail when the hash changed and the version did not, warn on a new version (printing the new hash), on a different resolved file (PATH shadowing) and when unpinned (printing the pin command). At use time (the 1Password status probe that the `op read` and `op item edit` paths run first) kit resolves, hashes once per process and compares before running a pinned `op`, refuses a mismatch without executing it or falling back, and exits non-zero naming the expected and actual hash and path. `kit tools pin --accept <tool>` is the only way to re-trust, and it writes an audit row first. Windows PATHEXT resolution is unit-tested on Linux only; macOS is unverified (no CI job runs it). Vendor signatures stay a manual step (`docs/THREAT_MODEL.md`).
