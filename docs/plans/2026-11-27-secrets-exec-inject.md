# `kit secrets` injects at exec time instead of writing `.env.local`

Status: DECIDED, option (a). Step 1 and the notice ship in 7.x; the default flips only in 8.0 (see
"Decision and what shipped"). The conflict below is why the flip waits for a MAJOR.

**Why:** kit-research `kms-decrypt-evidence-vs-kit` (2026-11-27). `kit secrets` takes a value from a
store whose reads are logged (for `aws-sm`, every `GetSecretValue` is a CloudTrail event) and
writes it to `.env.local`, where nobody records who reads it. The post's design rule, *"put the key
somewhere that forces an attacker to make a request you can see"*, says the opposite: keep the value
in the store, and hand it to one process at a time through a path kit records (`secrets.read`).

## Consumers of `.env.local` today (measured at the #1113 head)

| Consumer | What it does with `.env.local` | Under exec-time injection |
|---|---|---|
| `kit secrets` (`src/secrets.ts` `generateSecrets`) | writes it, `0600`, from `[secrets.keys]` or `[secrets].template` | resolves into memory; writes only with `--write-env-file` |
| MCP `kit_secrets` (`src/mcp-server.ts`) | writes it; returns `{ ok, written, writtenKeys, results }` | same as the CLI; `written` stays in the JSON (false unless asked) |
| `kit run` / MCP `kit_run` (`src/run.ts` `loadCommandEnvironment`) | reads it into the child env | resolves `[secrets.keys]` itself and injects into the child env; reads `.env.local` only if it exists (deprecation notice) |
| exec-broker (`src/exec-broker/broker.ts`) | hands `run()` the requested names from `process.env`; `kit run`'s callback then loads `.env.local` | unchanged: the injection happens in `kit run`'s callback, scoped and recorded |
| `kit setup` step 4 (`src/commands/setup.ts`, `src/setup-modes.ts`) | runs `cmdSecrets`, prints "Wrote .env.local", runs its commands through `executeCommand` | prints "resolved N keys; run your dev server with `kit run -- <cmd>`" |
| `kit secrets sync` | writes to `os.devNull` (no file) | unchanged |
| `kit secrets onecli register` (`readSecretValueFromVault`) | writes to a temp `.env` and deletes it | resolve in memory; no temp file |
| `kit doctor`, `kit statusline` | report "`.env.local` exists" as a health row | "secrets resolvable" instead; `.env.local` absent is no longer a failure |
| `kit env diff` / `env switch` / `env-inspect` / `project` (dashboard URLs) / `provision` | read or update `.env.local` | read the resolved env in memory; `env switch` stops telling the user to re-run `kit secrets` to "materialize prod values" |
| `check-client-exposure`, `scan-build`, `scan-plaintext`, `security-prescan`, `env-write-gate`, `check-gitignore` | treat `.env.local` as a file to protect or scan | unchanged: still guarded wherever one exists |
| Next.js | loads `.env.local` itself; lookup order is `process.env`, then `.env.$(NODE_ENV).local`, then `.env.local` (https://nextjs.org/docs/app/guides/environment-variables) | `kit run -- next dev`: the injected `process.env` wins, and no file is needed |
| Vite | loads `.env` and `.env.local` itself; *"environment variables that already exist when Vite is executed have the highest priority"* (https://vite.dev/guide/env-and-mode) | `kit run -- vite`: same. Only `VITE_`-prefixed names reach client code, as before |
| Other dev servers, ORMs, test runners that read `.env.local` (dotenv, `@next/env` `loadEnvConfig`) | read the file directly | `kit run -- <cmd>`; a tool that reads only the file and never `process.env` keeps needing `--write-env-file` |
| Docs | `README.md` (setup transcript, `kit_secrets`/`kit_run` rows), `docs/COMMANDS.md`, `docs/FEATURES.md` ("Materialize `.env.local`"), `docs/MCP_TOOLS_REFERENCE.md`, `docs/DATA_FLOW.md`, `docs/MIGRATION_GUIDE.md`, plugin and adapter guides | rewritten as below |

## Proposed least-breaking path

1. **Now (7.x, additive, no default change):**
   - `kit run` gains `--inject` (and `[secrets] inject = true`). It resolves `[secrets.keys]` into the
     child's environment through `generateSecrets`' resolver, with no file. Each run records
     `secrets.read` with `via: "kit run"` (#1126), and the values join #1113's redaction list.
   - A new `--write-env-file` flag on `kit secrets` is accepted as an explicit spelling of today's default (proposed, not yet a flag).
   - A new `--no-write-env-file` flag on `kit secrets` resolves and reports without writing (proposed).
   - Docs teach `kit run -- next dev` / `kit run -- vite` / `kit run -- <cmd>` as the recommended
     path.
2. **Deprecation notice, one release:** when `kit secrets` or `kit run` finds a `.env.local` whose
   header is kit's (`# Generated by kit secrets`), it prints one stderr line, never on stdout:
   *"kit 8 will stop writing .env.local by default; run `kit run -- <cmd>`, or pass
   `--write-env-file` to keep the file."*
3. **Next major (8.0), the default flips:**
   - `kit secrets` resolves in memory and writes nothing unless given `--write-env-file`.
   - `kit run` injects by default.
   - MCP `kit_secrets` follows the CLI, keeps `written` in its JSON, and adds `injected`.
   - The changelog carries a `BREAKING` entry, and `contracts/public-surface.json` is reviewed.

**Fail closed:** if a value cannot be resolved, or its read cannot be recorded, the proposed `--inject` mode of `kit run`
does not start the child. It never falls back silently to a stale `.env.local`.

**Windows:** env injection goes through `spawn`'s `env` option, which works the same on Windows.
Windows env names are case-insensitive, so the merge must not keep both `Path` and `PATH`. Fold
names case-insensitively on `win32` when the resolved keys are merged over the inherited env, and
test it on `win32`. Today's `.env.local` merge in `run.ts` does not fold.

## Migration text (for the changelog fragment and `docs/MIGRATION_GUIDE.md`)

> `kit secrets` no longer needs to write `.env.local`. Run your dev server through kit so it gets
> the values in its environment: `kit run -- next dev`, `kit run -- vite`, `kit run -- npm test`.
> Next.js and Vite take `process.env` ahead of `.env.local`, so nothing else changes. A tool that
> only reads the file still works when `kit secrets` is given `--write-env-file`. Then delete the old
> `.env.local`: every read of it was invisible to kit and to your vault's audit log.

## Conflict (why this stops at a draft)

`secrets` is a `stable` command (`contracts/public-surface.json`). `docs/CLI_STABILITY.md`
promises that a stable command *"keeps working with the same name and core behavior across the whole
major line"*. Its core behaviour, as documented, is writing the file:

- the help text (`src/cli.ts`): *"Generate .env.local from template + secret store"*;
- `docs/FEATURES.md`: *"`kit secrets`: Materialize `.env.local` from the configured vault store"*;
- `docs/MCP_TOOLS_REFERENCE.md` and `README.md`: *"`kit_secrets` … Generate `.env.local`"*;
- `kit setup`'s transcript in `README.md`: *"[4/6] Secrets ✓ Wrote .env.local"*.

Flipping the default inside 7.x breaks that promise. No ADR covers `.env.local` (`docs/adr` checked),
so this is a contract conflict, not an ADR one. Step 1 and the notice are additive and allowed in a
minor release. The flip needs the owner to schedule it for 8.0, or to amend `CLI_STABILITY.md`.

## Decision and what shipped

The owner chose (a): ship the opt-in pieces and the notice in 7.x, flip the default in 8.0.
`docs/CLI_STABILITY.md` ("Behaviour changes scheduled for the next MAJOR") records the flip, so the
7.x promise holds: every change below is additive.

Shipped in 7.x:

- `kit run --inject -- <cmd>` and MCP `kit_run` `inject: true` (`src/run-inject.ts`). They resolve
  `[secrets.keys]` through `resolveSecretsInMemory` (`src/secrets.ts`, the same resolver
  `generateSecrets` uses), record `secrets.read` with `via: "kit run"` first (#1126), and put the
  values in the child's environment, where #1113's declared-value redaction covers them.
  `.env.local` is neither read nor written. Fail closed: no `[secrets.keys]`, a prod-scoped key
  outside prod (the rule `kit secrets` applies), an unrecordable read, or any unresolved key stops the
  run before the child exists. Names fold case-insensitively on `win32` (`mergeInjected`).
- `kit secrets --write-env-file`: today's behaviour, spelled out.
- The notice: when `kit secrets` writes `.env.local` without `--write-env-file`, one stderr line
  points at `kit run --inject`. It fires on every write, not only when an existing kit header is
  found, because that is when the 8.0 change would affect the caller.

Not shipped, deliberately (each is open for 8.0 or a later minor):

- `[secrets] inject = true` in `.kit.toml` (a config-schema addition); `--inject` covers it.
- `--no-write-env-file`; in 8.0 it becomes the default and needs no flag.
- MCP `kit_secrets` is unchanged: it still writes and returns `written`. 8.0 adds `injected`.
- `kit run` without `--inject` still reads an existing `.env.local` and prints no notice, and the
  `.env.local` merge there still does not fold names on Windows.
- `kit setup`, `kit doctor`, `kit statusline`, `env switch` and the other consumers in the table
  keep their 7.x behaviour until the flip.

Scheduled for 8.0: `kit secrets` writes only with `--write-env-file`; `kit run` injects by default;
MCP `kit_secrets` follows the CLI and adds `injected`; the changelog carries a `BREAKING` entry and
`contracts/public-surface.json` is reviewed.

Consumers re-verified from their official docs (2026-11-28):

- Next.js, "Environment Variable Load Order": "1. `process.env` 2. `.env.$(NODE_ENV).local`
  3. `.env.local` (Not checked when `NODE_ENV` is `test`.)" —
  https://nextjs.org/docs/app/guides/environment-variables#environment-variable-load-order
- Vite, ".env Files": "environment variables that already exist when Vite is executed have the
  highest priority and will not be overwritten by `.env` files" — https://vite.dev/guide/env-and-mode
- dotenv: "By default, we will never modify any environment variables that have already been set." —
  https://github.com/motdotla/dotenv (`@next/env` `loadEnvConfig` is the Next.js loader above.)

`src/cli-run-inject.test.ts` quotes the first two, and drives the real CLI with a child that reads
only `process.env`, as `next dev` and `vite` do.
